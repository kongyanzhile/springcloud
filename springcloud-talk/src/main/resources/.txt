标准解法：连接态本地存 + 路由态和消息用中间件广播

1. sid → 实例的映射关系，用 Redis 存

连接建立时，每个实例把自己管理的 sid 写入 Redis（比如 websocket:sid:{sid} → 存这个实例的标识，或者简单用 Redis 的 Set/Hash 记录"这个实例持有哪些 sid"），断开时删除。这一步只是记录"谁在谁手里"，不是用来传消息的。

2. 真正推送消息走 Pub/Sub 广播，而不是查表后指定发送

业务方要给某个 sid 推消息时，不需要先查这个 sid 在哪个实例上，而是直接把消息发到一个 Redis 频道（或者 RocketMQ/RabbitMQ 的一个 topic），所有网关实例都订阅这个频道。每个实例收到广播消息后，检查自己本地的 CopyOnWriteArraySet 里有没有这个 sid 的连接：

有 → 通过本地的 Session 直接推送
没有 → 忽略，什么都不做

这样天然解决了"消息发到哪个实例"的路由问题，代价是消息会广播到所有实例（量不大的话完全没问题，这是业界最常见的做法）。

3. 如果连接量特别大，广播成本高，才需要精确路由

那才需要维护 Redis 里 sid → 实例 的精确映射，业务方推送前先查这个映射，直接把消息发到对应实例专属的 topic/channel。但这个复杂度比方案 2 高不少，一般用户量没到那个规模不建议一开始就上。
